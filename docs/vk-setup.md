# Уведомления о заявках в VK

Сайт сохраняет имя, телефон и необязательный комментарий в PostgreSQL, затем отдельный worker отправляет уведомление от сообщества VK в выбранный личный диалог или беседу. Сбой VK не отменяет принятую заявку. Для этой исходящей доставки не нужны отдельное VK-приложение, Callback API или постоянно работающий Long Poll обработчик.

## 1. Подготовьте сообщество

Создайте сообщество «Доверху» или используйте существующее. Нужны права владельца/администратора этого сообщества. В его управлении включите сообщения. В разделе работы с API создайте **ключ доступа сообщества** с разрешением на сообщения (`messages`). Не используйте пользовательский токен или сервисный ключ приложения. Названия пунктов интерфейса могут отличаться; ориентиры — «Сообщения», «Работа с API», «Ключи доступа».

Метод `messages.send` поддерживает токен сообщества; в проекте закреплена совместимая версия `5.199`, соответствующая опубликованной схеме. Это выбранная версия интеграции, а не утверждение о самой новой доступной версии API. [Официальная схема методов VKCOM](https://raw.githubusercontent.com/VKCOM/vk-api-schema/master/messages/methods.json), [ключи доступа VK](https://dev.vk.com/ru/api/access-token/getting-started).

## 2. Выберите получателя

Для личного диалога получатель открывает сообщество со своего аккаунта, разрешает ему сообщения и пишет первое сообщение. `VK_PEER_ID` — числовой ID этого пользователя, а не ID сообщества и не короткое имя страницы.

Для беседы включите возможности ботов и добавление сообщества в беседы, затем добавьте сообщество в нужную беседу. Числовой `peer_id` беседы имеет вид `2000000000 + chat_id`. Надёжнее получить его через `messages.getConversations` с токеном именно этого сообщества: нужное значение находится в `response.items[].conversation.peer.id`. Номер беседы в интерфейсе личного аккаунта может отличаться от доступного сообществу. [Методы сообщений и параметры peer_id](https://raw.githubusercontent.com/VKCOM/vk-api-schema/master/messages/methods.json).

Проект ожидает положительный `VK_PEER_ID` личного диалога или беседы. Отправка в другое сообщество не предусмотрена настройками этой интеграции.

## 3. Заполните серверное окружение

```dotenv
VK_GROUP_TOKEN=
VK_GROUP_ID=
VK_PEER_ID=
VK_API_VERSION=5.199
VK_TIMEOUT_MS=15000
```

`VK_GROUP_ID` — положительный числовой ID сообщества-отправителя. `VK_GROUP_TOKEN` вставляется напрямую в локальный/серверный `.env` или хранилище секретов хостинга; **в чат его присылать не нужно**. `.env` исключён из Git и Docker build context. Данные VK передаются только worker, frontend их не получает.

Для продолжения настройки можно сообщить разработчику:

- ссылку на сообщество или его числовой ID;
- ссылку/ID аккаунта получателя либо выбранную беседу и её `peer_id`;
- подтверждение, что получатель разрешил сообщения и токен уже записан в `.env`.

## 4. Включите доставку после подтверждения адресата

Сначала сделайте backup БД и остановите прежний worker. После сборки нового backend image примените `0002_vk_notifications.sql` отдельным `migrate` service, затем поднимите новые API и worker. Миграция сохраняет заявки и уже отправленную историю, присваивает outbox постоянные `random_id` и переносит только неотправленную очередь на VK.

```sh
docker compose stop worker
# После backup и сборки нового API image:
docker compose up --no-deps --no-build --force-recreate --exit-code-from migrate migrate
# Только после проверки миграции и подтверждения нужного peer_id:
docker compose up -d --no-deps --no-build --wait api worker
```

При запуске настроенного worker отправляются и ранее ожидавшие задачи. До явного выбора получателя оставляйте токен/ID пустыми. Проверочную реальную заявку отправляйте после подтверждения адресата. В коде нет автоматической отправки тестового сообщения при старте или вводе токена.

## Как обрабатываются ошибки

Успешный HTTP 200 ещё не означает доставку: VK может вернуть `error.error_code`. Полный ответ с `request_params` не сохраняется в логах, потому что он может содержать токен и параметры заявки. [Схема ошибок](https://raw.githubusercontent.com/VKCOM/vk-api-schema/master/errors.json), [объект ошибки](https://raw.githubusercontent.com/VKCOM/vk-api-schema/master/base/objects.json).

| Код                                                                  | Что проверить                                                                               |
| -------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| `vk_configuration_missing`                                           | Заполнены ли токен, ID сообщества и получателя                                              |
| `vk_api_5`, `vk_api_27`                                              | Действителен ли токен нужного сообщества                                                    |
| `vk_api_7`, `vk_api_15`                                              | Достаточно ли прав и доступа                                                                |
| `vk_api_901`, `vk_api_902`                                           | Получатель разрешил сообщения, настройки приватности допускают отправку                     |
| `vk_api_912`, `vk_api_917`, `vk_api_922`, `vk_api_927`, `vk_api_932` | Бот включён, добавлен в существующую доступную беседу и может взаимодействовать с адресатом |
| `vk_api_14`                                                          | VK требует ручного подтверждения/captcha                                                    |
| `vk_api_6`, `vk_api_9`, `vk_api_29`                                  | Ограничение частоты или flood control; worker повторит позже                                |
| `vk_api_10`, `vk_http_503`, `vk_network_error`                       | Временный сбой VK или сети; заявка остаётся в БД                                            |

Обычные повторы используют увеличивающуюся задержку; ошибки прав/настроек — минимум час. Ограничения числа попыток нет. После исправления настроек прежний `random_id` сохраняется. Не сбрасывайте identity sequence при переносе БД: одному уведомлению должен соответствовать один устойчивый ID. Независимые инсталляции с одним сообществом не должны выдавать пересекающиеся ID.

Публичная схема описывает `random_id` как защиту от повторной отправки, но не фиксирует область и срок дедупликации. Поэтому интеграция сохраняет надёжную очередь и стабильный ID, не обещая exactly once. [Параметр random_id и messages.send](https://raw.githubusercontent.com/VKCOM/vk-api-schema/master/messages/methods.json), [формат успешного ответа](https://raw.githubusercontent.com/VKCOM/vk-api-schema/master/messages/responses.json).
