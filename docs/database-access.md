# Доступ к базе данных

API и обработчик VK подключаются к PostgreSQL от имени разных ограниченных ролей. Административное подключение используется для миграций, резервного копирования и обслуживания. Для обычной работы сайта административные права не нужны.

## Роли и права

| Роль                                           | Что разрешено                                                                                                  |
| ---------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| `POSTGRES_USER` (по умолчанию `povod`)         | Администратор PostgreSQL, владелец базы и схемы; применяет миграции и настраивает рабочие роли                 |
| `DB_API_USER` (по умолчанию `povod_api`)       | Добавлять заявки и задачи outbox; читать только `id` и `client_request_id` заявки для ответа и идемпотентности |
| `DB_WORKER_USER` (по умолчанию `povod_worker`) | Читать заявки и outbox для доставки; менять только поля обработки уведомления                                  |

Worker может обновлять в `notification_outbox` только `status`, `attempts`, `next_attempt_at`, `locked_at`, `locked_by`, `last_error`, `updated_at`, `sent_at`. Он не может менять имя, телефон и комментарий заявки, ID, payload или стабильный `random_id` уведомления. API не может читать контактные данные уже сохранённых заявок или обновлять очередь после вставки.

Обе рабочие роли имеют `LOGIN`, но не имеют `SUPERUSER`, `CREATEDB`, `CREATEROLE`, `REPLICATION`, `BYPASSRLS` и наследования прав. Они не владеют объектами, не состоят в других ролях, не могут делать `DELETE`, `TRUNCATE`, менять структуру таблиц, создавать схемы/временные таблицы или обращаться к журналу Drizzle. Доступ к PostgreSQL и схеме приложения выдан явно. Общие права `PUBLIC` на рабочую базу и схемы ограничиваются при настройке. На уровне PostgreSQL права могут задаваться для отдельных столбцов; владение объектами даёт отдельные полномочия, поэтому оно остаётся у администратора. [Документация GRANT](https://www.postgresql.org/docs/17/sql-grant.html).

## Переменные окружения

```dotenv
POSTGRES_DB=povod
POSTGRES_USER=povod
POSTGRES_PASSWORD=<пароль администратора>
DB_API_USER=povod_api
DB_API_PASSWORD=<отдельный пароль API>
DB_WORKER_USER=povod_worker
DB_WORKER_PASSWORD=<отдельный пароль worker>
```

Используйте три независимых случайных пароля. Подходит пароль из 32 случайных байтов, представленных 64 hex-символами: он безопасно включается в URL без дополнительного кодирования. Сгенерируйте значения в менеджере паролей и сохраните непосредственно в `.env`; не отправляйте их в чат, логи или репозиторий. Для автоматической генерации в новой, ещё не запущенной установке можно выполнить следующую команду после копирования `.env.example` в `.env` — она записывает пароли в файл, не выводя их:

```sh
node --input-type=module -e "import { readFileSync, writeFileSync } from 'node:fs'; import { randomBytes } from 'node:crypto'; const path = '.env'; let text = readFileSync(path, 'utf8'); for (const key of ['POSTGRES_PASSWORD', 'DB_API_PASSWORD', 'DB_WORKER_PASSWORD']) { const pattern = new RegExp('^' + key + '=.*$', 'm'); if (!pattern.test(text)) throw new Error('Missing variable: ' + key); text = text.replace(pattern, key + '=' + randomBytes(32).toString('hex')); } writeFileSync(path, text, { mode: 0o600 });"
```

Эта команда предназначена только для первого запуска: она не меняет пароль уже существующей административной роли PostgreSQL. Также она не обновляет native URL — их нужно синхронизировать отдельно. Ограничьте доступ к файлу учётной записью владельца сервера: при перезаписи существующего файла его старые разрешения сохраняются; на Windows доступ регулируется ACL. Не публикуйте полный `docker compose config` или `docker inspect`: они могут содержать подставленные секреты.

В Compose параметры `DB_*` нужны сервису `migrate` для настройки ролей. API и worker получают только собственный `DATABASE_URL` с внутренним адресом `postgres:5432`; пароль администратора и пароль соседнего сервиса им не передаются. У сервиса PostgreSQL остаются его административные `POSTGRES_*`. Токен VK получает только worker.

Для запуска Node.js вне контейнеров используются три URL:

```dotenv
DATABASE_URL=postgresql://povod_api:<пароль API>@localhost:5432/povod
WORKER_DATABASE_URL=postgresql://povod_worker:<пароль worker>@localhost:5432/povod
MIGRATION_DATABASE_URL=postgresql://povod:<пароль администратора>@localhost:5432/povod
```

Подставьте пароли соответствующих ролей; при использовании других имён, базы или порта измените все URL. Значения со специальными URL-символами требуют percent-encoding. Native worker выбирает `WORKER_DATABASE_URL`, миграции — `MIGRATION_DATABASE_URL`; если соответствующий URL не задан, используется `DATABASE_URL`. В Compose этот fallback штатный: персональный `DATABASE_URL` уже задан каждому процессу. Для native запуска заполняйте все три URL, чтобы миграции не пытались подключиться ограниченной ролью API.

## Первая установка

После настройки `.env` обычный production запуск остаётся прежним:

```sh
docker compose config --quiet
docker compose up -d --build --wait
```

`migrate` ждёт готовности PostgreSQL, проверяет конфигурацию рабочих ролей, применяет SQL migrations и настраивает роли. API и worker запускаются только после успешного завершения. Инициализация работает с новой базой и существующей схемой: заявки и очередь не очищаются, прежние SQL migrations не переписываются.

Для native разработки сначала поднимите PostgreSQL и выполните миграции с административным URL:

```sh
docker compose -f compose.dev.yml up -d --wait
pnpm db:migrate
pnpm dev
```

Worker запускается в отдельном терминале командой `pnpm --filter @gift/api dev:worker`. В production отсутствие нужных паролей и частичная конфигурация ролей завершают миграции ошибкой. В режиме разработки/тестов настройка ролей может быть пропущена, только если не задан ни один параметр `DB_API_*`/`DB_WORKER_*`: это допускает изолированные тестовые базы, но не заменяет настройку рабочих ролей для обычного запуска.

## Обновление существующей установки

1. Подготовьте отдельные имена и пароли API/worker в `.env`; сохраните текущие административные реквизиты, имя базы и volume. Пересоберите backend: `docker compose build api`.
2. Остановите процессы, которые пишут данные: `docker compose stop api worker`.
3. Сделайте резервную копию PostgreSQL административной ролью и проверьте её восстановлением в отдельную базу. Зафиксируйте количество заявок/outbox и контрольные суммы сохраняемых полей. Копия содержит персональные данные; храните её с ограниченным доступом.
4. Примените миграции и настройки доступа: `docker compose run --rm migrate`. При ошибке исправьте конфигурацию и повторите этот шаг; не запускайте новую версию до успешного завершения.
5. Пересоздайте процессы с новыми подключениями: `docker compose up -d --no-deps --force-recreate api worker`.
6. Проверьте `docker compose ps`, готовность `/api/health/ready`, сохранность исходных данных и права обеих ролей. Контрольную заявку с доставкой создавайте только в согласованный тестовый адресат; проверку очереди без внешнего сообщения можно проводить с остановленным worker.

Права на конкретные объекты пересоздаются при каждом запуске `migrate`, даже когда новых SQL migrations нет. Настройка ролей выполняется транзакционно после Drizzle migrations; ошибку этого шага нужно исправить повторным запуском команды. Уже успешно применённые SQL migrations при этом не откатываются автоматически.

Существующая роль с подходящим именем используется повторно только при наличии служебной метки, связывающей её с этой базой и сервисом. Чужая, привилегированная роль, владелец объектов или участник других ролей отвергается без переназначения её прав. При таком конфликте выберите новое уникальное имя в `DB_API_USER`/`DB_WORKER_USER`; не передавайте приложению существующую административную роль. Роли PostgreSQL общие для кластера: нескольким установкам в одном кластере нужны разные имена рабочих ролей.

Не удаляйте volume и не используйте `docker compose down -v` для смены прав. Старое административное подключение больше не передаётся API/worker; сама административная роль сохраняется для обслуживания базы.

## Смена паролей и развитие схемы

Для смены рабочих паролей задайте новые `DB_API_PASSWORD` и/или `DB_WORKER_PASSWORD`, остановите API/worker, повторно выполните `docker compose run --rm migrate`, затем пересоздайте процессы. Для native режима синхронно обновите соответствующие URL. Смена имени создаёт отдельную роль; прежняя роль не удаляется автоматически — администратор должен отключить/удалить её после проверки отсутствия использования.

`POSTGRES_PASSWORD` обрабатывается отдельно: PostgreSQL Docker image применяет его при инициализации пустого volume. В уже существующем кластере сначала меняют пароль административной роли средствами PostgreSQL, затем синхронизируют `.env` и `MIGRATION_DATABASE_URL`. Не оставляйте административный пароль в URL API/worker. [Документация ALTER ROLE](https://www.postgresql.org/docs/17/sql-alterrole.html).

Новые таблицы, sequences и дополнительные действия не получают права автоматически. Изменяйте явный перечень разрешений рядом с кодом настройки ролей, затем проверяйте разрешённые запросы и отказ в запрещённых операциях на отдельном PostgreSQL. Не добавляйте `GRANT ALL` или широкие default privileges для обхода ошибки `permission denied`.

## Резервная копия и восстановление

Обычный `pg_dump` сохраняет одну базу, но не глобальные роли кластера. Поэтому рабочая резервная копия должна сопровождаться защищённой конфигурацией развёртывания и процедурой повторной настройки ролей. Административные учётные данные нельзя хранить в публичном отчёте рядом с копией. [Документация pg_dump](https://www.postgresql.org/docs/17/app-pgdump.html).

При проверке копии создайте отдельную базу под административной ролью и восстановите дамп с `pg_restore --no-owner --no-privileges`. Эти параметры не восстанавливают прежних владельцев/ACL: ими управляет текущая конфигурация. После восстановления выполните миграции с URL восстановленной базы и уникальными именами тестовых ролей — они получают служебную метку именно этой базы. Проверьте данные и очередь до запуска worker. Не подключайте worker восстановленной копии к реальному VK-получателю: в копии могут оставаться неотправленные уведомления.

Для переноса production в новую базу того же кластера тоже задайте новые `DB_API_USER`/`DB_WORKER_USER`, новые пароли и соответствующие native URL: метка прежних ролей содержит OID старой базы, и использовать их с новой базой настройка намеренно не позволит. Прежние роли сохраняются для старой базы до отдельного отключения администратором. В новом кластере, где этих ролей ещё нет, можно использовать прежние имена — они будут созданы заново. Восстановление production выполняется при остановленных API/worker; запускать их следует только после успешной настройки ролей и проверки сохранности данных. Volumes переживают пересоздание контейнеров, но не заменяют резервные копии на отдельном носителе.
